WEBSITE REBUILD PROMPT: COMPLETE DATA SCIENCE COMMUNITY WEBSITE
Structure and behavior specification. No existing records, personal data or credentials.
Snapshot of the implemented project: 12 October 2026.

Build the complete website described below. Implement working public pages, authenticated dashboards, private administration, persistent storage and synchronized editing. Do not deliver a static mockup. Use this document as a reconstruction prompt and acceptance checklist. Supply configurable content and empty collections instead of copying real people, accounts, applications, event records, projects, uploads or private information.

1. PURPOSE AND IDENTITY
Create an independent student data-science community website for students throughout Pakistan. Keep it suitable for future national expansion. Do not affiliate it with a particular university or place a university logo anywhere. Institution names belong only in user-supplied profiles and application answers. Community name, logo, contact details, social links, headings and theme must be configurable by the administrator. Use placeholders for all owner-specific details and credentials. Do not fabricate finished projects, confirmed events, member achievements, statistics or team identities. Label practice briefs and planned events honestly.

2. DESIGN AND COMMON PAGE STRUCTURE
Use a clean, comfortable, light interface: white backgrounds, navy text, blue accents approximately #165dff, pale blue panels, restrained borders, generous spacing and readable Inter-style typography. Use a simple infinity-style society mark that can be replaced through administration. Use a dark blue feature panel for the homepage game and blue sidebar styling for the administrator. Keep student, society-member and ambassador workspaces visually distinct through their headings, welcome panels, badges, actions and reputation indicators while retaining the same brand.
Every public page has a responsive navigation header, a skip-to-content link, a clear main heading, readable content sections and a consistent existing footer. Navigation includes Start here, About, Projects, Events, Resources, Community, sign-in/account actions and an accessible expandable menu. Additional pages remain discoverable through menus and footer links. Mark the current navigation item. Collapse navigation appropriately on phones. Do not hide essential reading content behind fixed-height panels or crop full page content. Provide real scrolling, working links, meaningful detail pages and clean empty states. Prevent horizontal overflow at phone, tablet and desktop sizes.
The footer contains brand information, discovery links, participation links, contact action, copyright, social links and the country label Pakistan. Directly BELOW Pakistan put ONE very small text button labelled Stop Animation, with the same small text styling. Do not add another footer, a full-width animation strip or separate pause buttons beside activities. Change it to Resume Animation when paused. Persist the preference across pages and browser tabs; respect reduced-motion device settings. Pause decorative CSS animation and reveal effects without disabling controls or gameplay. On login and portal layouts, retain one discreet text control within their existing layout rather than creating a special footer. Pause motion when the page is hidden or artwork is offscreen.
Provide keyboard access, visible focus, associated form labels, semantic buttons, useful image descriptions, readable contrast, touch-friendly primary controls and status/error messages. Do not use alert spam or imply that a failed save succeeded.

3. COMMUNITY ROLES AND AUTHORIZATION
Expose exactly THREE community modes: Normal member (internal role student), Society member (internal role member), and Ambassador (internal role ambassador). New verified users start as normal members. Administrator is a separate private management identity, not a fourth community registration choice. Never let a public user select or promote themselves to administrator.
Cabinet membership is an appointed position on a society-member account, not another community mode. Only a society member with a cabinet position receives the cabinet assigned-work option. Ambassadors may also receive assigned work. Administrators can assign work to themselves through administration.
Keep account status separate from role: pending, approved, rejected or suspended. Keep membership and ambassador application review states separate from account status. A pending application must not remove an approved user's existing normal account or prematurely change their role. An administrator approves/rejects the application and applies any role change. Suspended or unauthorized accounts cannot bypass gates by knowing a URL or calling an API directly. Server-side authorization must control every private action and return only the current user's private records.

5. HOMEPAGE CLASSIFICATION ARCADE
Replace generic waves and the basic click-the-outlier quiz with a custom interactive data-science activity. Use a dark navy/blue panel, glowing model boundary, blue circle and mint diamond classes, subtle animated signals and a responsive SVG plot. The three missions are: separating streams with a straight boundary; separating an inner orbit from outer points using a circular boundary; and learning a curved/noisy frontier with a wave boundary. These are mathematical classification tasks, not a trivial multiple-choice question.
Let the user select Linear, Orbit or Wave models and adjust relevant sliders for tilt, position, radius or bend. Hide irrelevant sliders. Display training fit and an unseen-data score only after a test. Generate approximately 28 training observations and 64 unseen observations, including limited label noise in the third mission. Allow five tests per mission. Unlock the next mission on a strong test result (about 86%) or after using the test allowance so a beginner cannot become trapped. Show helpful feedback, mistake rings and a reset-mission action. Completing the third mission offers a new run with varied observations. Do not present this recreational activity as an assessed course or certificate qualification. Its heading and introductory wording must be editable by admin. Its animation obeys the shared footer preference; the activity itself stays usable while motion is paused.

6. AUTHENTICATION AND ACCOUNT PAGES
Use Node.js server-side authentication with WorkOS AuthKit for production member login. Support verified email and configured Google/Gmail sign-in; allow other configured provider options such as GitHub without introducing new society modes. Implement /auth/login, /auth/signup and /callback with signed browser-bound state, expiry checks, verified-email validation and sealed session cookies. Configure the provider externally using owner-supplied secrets; never embed credentials in frontend JavaScript. The login UI must reflect whether production authentication is configured rather than pretending a mock login is real.
/login.html is the account entry page, with configurable welcome heading and copy, secure create-account/login actions and a appropriate role-aware dashboard destination. Handle existing sessions correctly. In isolated local development, support local email/password registration/sign-in with securely hashed passwords, password change and expiring reset links. Do not expose local administrator bootstrap in production. Authentication failures and provider failures must leave useful retry/sign-in states, not broken pages.
On sign-out revoke the provider session, persist a block against replay of the old website session, clear cookies and return to the public homepage. Use HttpOnly, SameSite cookies and Secure in HTTPS production. Password changes revoke other local sessions. Never display or log raw passwords, keys, sealed cookies or callback tokens.
/member-dashboard.html, /student-dashboard.html and /ambassador-dashboard.html are authenticated portal routes. Render the user's REAL current role; a user must not gain another interface's privileges by changing the URL. Administrator requests for community dashboards route back to private administration, except for authenticated synthetic CMS previews.

Provide one published, very simple open starter and a later member pathway covering data cleaning, dashboard/storytelling, investigation/research and predictive-model evaluation. The PDF must explain, in the student's own words, what they did, what they learned and the result, plus project-specific methods/limitations. Use an authenticated ownership-checked certificate endpoint rather than exposing a private source URL. Private uploaded certificates must stay inaccessible to other users, including by guessing a file URL, and inaccessible after certificate/access revocation. External Drive sharing permissions remain the owner's responsibility. Allow admin to replace/revoke certificates. No certificate or award for the starter or a rejected AI-written report.
General society contributions similarly require a project/work link and a separate Drive PDF report, administrative review and the same written-report policy.

12. CMS PUBLICATION AND LIVE SYNCHRONIZATION
Keep draft content separate from published content. Explicit Save draft stays private. Apply/edit settings normally saves and publishes through the current Publish-on-apply behavior. Publication and settings writes must be atomic and revision-checked; reject stale conflicting revisions rather than silently overwrite another device's work. Retain a bounded publication history and audit important actions.
Track content/draft revision, published revision and overall state revision. Public and account pages poll a lightweight revision endpoint approximately every 500 ms while visible. Fetch published content when its revision changes. Role, assignment, application, submission and certificate changes must also refresh the affected state even if no public-content revision changed. The administrator project/task boards refresh after remote student actions. Use BroadcastChannel for quicker same-browser notification and refresh on focus/visibility return. An optional server changes stream may supplement polling; polling must work in serverless production.
Do not refresh over a user's active text input, open modal, unsaved draft or in-progress save. Queue needed refreshes and apply when safe. Preserve project form values during relevant updates. Avoid duplicate polling loops. Stop timers on page exit and restore them correctly on return. Show save failures and do not declare changes live before database commit.

13. PERSISTENT DATABASE AND STORAGE ARCHITECTURE
Use a Node.js 22+ backend with the pg PostgreSQL client, WorkOS server SDK, regular HTML/CSS/JavaScript pages and an authorized same-origin API. The current design does not require React, Next.js or a hosted Sanity studio. Use Tailwind-built utility CSS plus custom styles, local fonts and a small local icon bundle. Supply package/build/start/test commands and modular server code.
Production requires a server-only PostgreSQL DATABASE_URL; Supabase PostgreSQL with verified TLS is a compatible provider. Browser clients must NOT directly query private tables or use a public anon key as a database password. Do not include a real provider project ID, connection URI, password or certificate secret in this prompt or frontend. A public CA certificate is configuration, not an account credential.
Implement these server-owned structural tables (no rows are supplied):
  public.dss_state: id integer primary key restricted to id = 1; data jsonb not null.
  public.dss_files: name text primary key; data bytea not null.
Enable row-level security and revoke direct grants from PUBLIC and browser anon/authenticated roles. A privileged server connection performs authorized application operations. Initialize schema/empty state transactionally. State storage is currently a serialized application document rather than one SQL table per feature; reproduce working transactional behavior and leave future normalization as an improvement, not a fictional current implementation.
The application state structure includes users and profiles; local/private-admin sessions and authentication revocation/failed-attempt metadata; membership/ambassador applications and drafts; event registrations; bookmarks; campus activities; general contributions; private tasks; coursework assignments/submissions/reviews/certificates; inquiries; upload metadata; audit entries; published CMS content; draft CMS content; publication history; revisions; and any compatibility learning-progress records. Use IDs and owner relationships, timestamps and safe status values. Do not populate actual private records. File bytes are separate in dss_files.
CMS content structure includes siteSettings, heroSection, pillars, theme, pageHeaders, per-element pages overrides, added blocks, portal wording/visibility settings, two application configurations, banners and collections. Use the collection families listed in section 11 with appropriate fields. Keep public catalog projects separate from learningProjects and per-user coursework.
For writes, reload state under a transaction/row lock, authorize/validate, mutate, store and COMMIT before sending success or setting successful session cookies. Roll back failed commits and ensure subsequent requests recover. Serialize conflicting writes across server instances. Read-only requests fetch state without acquiring the write lock or doing accidental writes. Protect staged response headers until commit succeeds.
Without DATABASE_URL in isolated local development, use a durable private JSON file and private uploads directory with serialized atomic temporary-file/rename writes. Support a separate DSS_DATA_DIR for testing/preview so it never overwrites real accounts. Vercel temporary filesystem is not a substitute for production persistence. Back up data before migrations; preserve existing records and custom CMS edits when introducing new structure/defaults.
